# v13.0.0 — 05.10.2026

Grundlage: Repo-Stand `0aa7949` (12.0.0, Commit vom 05.10.2026).

Änderung an der Datenstruktur (neue Tabelle `kategorie`), daher 13.0.0.

## Was wurde geändert und warum

Bei „＋ neue Kategorie …“ konnte man nur den Buchstaben für den Code
eingeben. Die Namen der Kategorien standen fest in der App (A Antrieb,
B Bremse, C Cockpit & Vorbau, L Laufrad & Reifen, R Rahmen,
W Werkstattmaterial); jeder neue Buchstabe hieß nur „Kategorie X“. Für eine
neue Kategorie „Orga“ (Kühlbox, Montageständer, …) braucht es einen Namen.

### Datenbank
- Neue Tabelle `kategorie` (Buchstabe → Name, beides eindeutig).
- Die sechs bisherigen Kategorien werden mit ihren bisherigen Namen
  eingetragen.
- Ohne Anmeldung: lesen, anlegen, umbenennen — nicht löschen.

### App
- Formular Neues Einzelstück / Neuer Artikel, Kategorie „＋ neue Kategorie …“:
  zwei Felder „Name der neuen Kategorie“ und „Buchstabe im Code“.
  Der Anfangsbuchstabe des Namens wird als Buchstabe vorgeschlagen, wenn er
  frei ist; ein selbst eingetragener Buchstabe wird nicht mehr überschrieben.
- Ist der Buchstabe schon vergeben (mit Namen oder in einem Code), zeigt die
  Vorschau das direkt an und Speichern wird abgelehnt. Ebenso bei einem Namen,
  den es schon gibt.
- Beim Speichern wird zuerst die Kategorie angelegt, dann das Teil/der
  Artikel. Schlägt das Anlegen des Teils danach fehl, bleibt die (leere)
  Kategorie stehen und steht in der Auswahl — nicht schlimm.
- Mehr → Tags → Kategorie: neuer Knopf „Name ändern“. Damit bekommen auch
  Buchstaben einen Namen, die bisher nur in Codes vorkamen („Kategorie X“).
  Codes und Etiketten ändern sich nicht.
- Alle Stellen mit Kategorienamen (Filter, Überschriften, Auswahl, Export)
  nehmen die Namen jetzt aus der Datenbank.
- Fehlt die Tabelle noch (Migration nicht ausgeführt), läuft die App wie
  bisher mit den festen Namen; das Namensfeld und „Name ändern“ erscheinen
  dann nicht.

## Manuelle Schritte (in dieser Reihenfolge)
1. Neon SQL-Editor → `db/migration_13.0.0.sql` komplett ausführen
   (vorher muss `db/migration_12.0.0.sql` gelaufen sein).
2. Data API → „Refresh schema cache“.
3. Dateien hochladen.

Es werden keine Dateien gelöscht oder umbenannt.

## Geprüft
- JavaScript-Syntax (`node --check`).
- Lokal in Postgres 16: Schema 12.0.0 + Migration 13.0.0 ergibt dasselbe
  Schema (Tabellen, Rechte, Policies) wie die neue `schema.sql`.
- Als Rolle `anonymous`: Kategorie anlegen, per Upsert umbenennen,
  `stueck_anlegen('O', 2, …)` → `O-201`; Löschen wird verweigert, doppelter
  Name wird verweigert.
- Browser (Playwright, Data API gemockt): neues Einzelstück mit neuer
  Kategorie „Orga“ → Vorschlag O, Vorschau O-201, Speichern schickt erst
  `kategorie`, dann `stueck_anlegen`; danach steht „Orga · O-2xx“ in der
  Auswahl. Belegter Buchstabe (R) wird angezeigt. „Name ändern“ unter
  Mehr → Tags schickt den Upsert. Ohne Tabelle: kein Namensfeld, feste Namen.

Nicht gegen die echte Neon-Datenbank getestet (insbesondere der Upsert mit
`on_conflict` über die Data API).

## Bekannte offene Punkte
- Kategorien lassen sich in der App nicht löschen (bewusst; leere
  Kategorien stehen in der Auswahl).
- Die Liste `BUCHSTABEN` im Code bleibt nur noch als Rückfall ohne Migration.
